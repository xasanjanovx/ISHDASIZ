## Подготовленный способ работы

Бот принимает сообщения через HTTPS webhook сайта, отдельный постоянно работающий сервер не нужен. Обработчик дожидается завершения update перед ответом, сохраняет возможность повтора при сбое и использует Node.js с бюджетом выполнения до 300 секунд. Настройка использует max_connections=1, чтобы ограничить одновременную доставку в экземпляры serverless; это ограничивает пропускную способность и не заменяет распределённую блокировку. Реальное время ответа и повторная доставка проверяются после публикации тестовым аккаунтом.

Ежедневные импорт и обновление справочников остаются в Vercel. Частый запуск очереди Telegram перенесён в подготовленный Supabase Cron: каждые 5 минут вызывается фиксированный адрес https://ishdasiz.uz/api/cron/sync-telegram-channels. CRON_SECRET берётся во время вызова из Vault и передаётся в заголовке Authorization. В SQL и расписании нет значения ключа; функция недоступна anon, authenticated и service_role. Обработчик использует существующую аренду очереди и квитанции доставки.

Это использует текущие сервисы, но не отменяет их квоты. Бесплатный Supabase может приостанавливать неактивные проекты; при исчерпании лимитов Vercel/Supabase работа может остановиться. Платные SMS и AI-запросы в ходе проверки не запускались; их существующие провайдеры и лимиты остаются отдельными условиями проекта. Платный тариф, trial или новая подписка не подключались.

Не применять историческую папку миграций целиком. Первая новая миграция создаёт отсутствующие служебные таблицы, сразу закрывает browser-доступ и сохраняет существующие квитанции/очередь/аренды при повторе. Она не устанавливает устаревшие триггеры публикации. Поздняя миграция добавляет отсутствующий post_to_channel как NULL, не выдавая согласие на публикацию.
4. В Extensions Supabase включить pg_cron и pg_net. Выполнить supabase/operations/install-channel-schedule.sql под postgres. Расписание создаётся **выключенным**, HTTP не отправляется. Повтор установки также оставляет его выключенным. Эти операционные файлы не входят в 33 миграции.
5. Проверить сайт, вход, восстановление закрытого аккаунта, обязательность своего резюме для отклика, переписку, поиск по 14 регионам и форматы работы тестовыми аккаунтами. Проверить Production GET /api/telegram/webhook: configured=true. Защищённый GET /api/telegram/set-webhook проверяет Telegram без переключения. Только затем выполнить защищённый POST для установки webhook, сохраняя накопленные updates. Проверить сообщение и callback через реальный Telegram.
6. После проверки прав бота в нужных каналах и тестовой доставки выполнить supabase/operations/activate-channel-schedule.sql. Активация проверяет ключ Vault, функции очереди и точную конфигурацию задания; сама не отправляет HTTP. Убедиться, что следующий запуск завершил HTTP с ожидаемым 200 и отражает настоящие результаты доставки.
7. Для остановки следующих запусков есть supabase/operations/pause-channel-schedule.sql. Уже отправленный HTTP может завершиться. Откат сайта к версии до серверных функций потребует совместимого восстановления схемы; простого Vercel rollback недостаточно.

Cron job history подтверждает выполнение SQL, а не успех HTTP. После запуска сопоставлять request_id из результата задания с id в net._http_response, проверять status_code, timed_out и безопасные счётчики JSON-ответа. Не выгружать net.http_request_queue: в её заголовках находится ключ. Не включать раскрытые Vault-значения в журналы. История cron.job_run_details автоматически не очищается; хранение и обслуживание оценить после реального запуска, без удаления истории в этом выпуске.

## Дополнение 12 октября: резервная копия без смены тарифа

Панель Backups подтверждает, что Free не включает резервные копии. Подготовлен npm run backup:database: согласованный архив public и supabase_migrations через бесплатный Session pooler, скрытый ввод существующего пароля базы, закрытая папка private-backups вне Git, проверка всех блоков архива и SHA-256. npm run test:backup проверяет настоящее копирование и восстановление на изолированном локальном PostgreSQL, без обращений к рабочему Supabase. Это не копия Auth/Storage/Vault/настроек хостинга; реальные данные ещё не скопированы и их восстановление не подтверждено. Порядок и границы — в docs/database-backup.md.
