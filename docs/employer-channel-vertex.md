# Вакансии работодателей в @ishdasiz и Vertex AI

Работодатель в @IshdasizBot выбирает «Разместить вакансию», затем ручную форму или создание из текста. Текст и подпись пересланного поста разбираются в черновик. Перед сохранением работодатель проверяет карточку, выбирает регион и подтверждает публикацию. Внешняя отправка проходит через существующую очередь с квитанциями доставки, повторами и снятием недоступных объявлений.

Шаблон и правила извлечения адаптированы из FLOW. ИИ сохраняет указанные факты и контакты, удаляет рекламу источника, не подставляет Ташкент или зарплату по умолчанию. Зарплата в USD/EUR сохраняется текстом и не записывается как сумма в UZS. Длинный пост содержит ссылку на полную вакансию; контакты сохраняются в карточке. Ошибка провайдера оставляет исходный текст в сессии и чате, с переходом к ручной форме. Для ИИ используется общий лимит аккаунта — 3 запроса в час.

Вакансии с `source=local` направляются в **@ishdasiz**. Импортированные вакансии и резюме сохраняют региональную маршрутизацию. Миграция не создаёт массовую очередь для старых вакансий. Повтор подтверждения одной формы использует сохранённый UUID объявления.

## Настройки сервера

Все вызовы моделей Gemini в чате, поиске, помощнике резюме и черновиках вакансий используют `lib/ai/vertex-client.ts` и Vertex AI express mode:

```dotenv
GOOGLE_CLOUD_API_KEY=<ключ Vertex AI express mode>
VERTEX_MODEL=gemini-2.5-flash
VERTEX_VACANCY_MODEL=gemini-2.5-flash
VERTEX_FALLBACK_MODEL=gemini-2.5-flash-lite
```

Также поддерживается имя `gemini_cloud_api` из существующего локального `.env`. `GOOGLE_CLOUD_API_KEY` имеет приоритет. Старый `GEMINI_API_KEY` больше не используется. Ключ передаётся заголовком `x-goog-api-key`; обращения к Developer API и зависимость `@google/generative-ai` удалены. Ключи находятся только в игнорируемых локальных файлах или секретах хостинга.

Протокол: [официальный справочник Vertex express mode](https://docs.cloud.google.com/gemini-enterprise-agent-platform/reference/express-mode/api-reference). Это авторизация express mode по API-ключу, без подмены её авторизацией service account.

## Включение в работающем сервисе

Нужны согласованные версии сайта и отдельного polling worker, если он используется. Сейчас Telegram сообщает о webhook на `ishdasiz.uz`; второй polling-процесс запускать не требуется.

1. Приостановить существующее расписание синхронизации каналов на время переключения.
2. Установить новый облачный ключ в серверном окружении, развернуть изменения сайта и используемого worker.
3. Сверить историю миграций и применить `supabase/migrations/20261027090000_main_employer_channel.sql` после существующей миграции `20261010130000_channel_deliveries.sql`. Не запускать весь исторический релиз повторно без проверки базы.
4. Выполнить `npx tsx scripts/check-bot-channel.ts` из настроенного каталога. Проверка читает права Telegram, состояние webhook и целевой канал в базе; она не отправляет постов и не меняет webhook.
5. Возобновить существующее расписание и проверить одну настоящую вакансию работодателя: подтверждение → запись сайта → пост @ishdasiz → закрытие и снятие поста.

Код хранится в Git отдельно от серверных секретов. Отправка ветки в GitHub сама по себе не устанавливает ключ в окружение хостинга и не применяет SQL.
