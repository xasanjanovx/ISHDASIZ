# ISHDASIZ

Сайт поиска работы по всему Узбекистану (RU/UZ) и Telegram-бот @ishdasizbot.
Подготовленные исправления описаны в [отчёте](docs/repair-report-2026-10-06.md). Локальные проверки не означают, что изменения уже выпущены.

## Разработка и проверки

Node.js 20.9 или новее. Для разработки используйте отдельную тестовую базу и тестовый бот.

```sh
npm ci
npm run dev
npm run typecheck
npm run lint
npm test -- --runInBand
npm run test:db
npm run build
```

Файлы окружения не публикуются. Значения секретов задаются в настройках хостинга; не вставляйте их в отчёты или переписку.

## Доставка сообщений бота

Выберите один способ: webhook сайта либо один постоянно работающий polling-процесс. Несколько poller-процессов одновременно не поддерживаются.

Webhook использует `/api/telegram/webhook`. Нужны `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET`, `TELEGRAM_SETUP_SECRET` и `NEXT_PUBLIC_APP_URL=https://ishdasiz.uz`. Инспекция через защищённый GET `/api/telegram/set-webhook` ничего не меняет. Защищённый POST этого маршрута настраивает webhook; перед переключением остановите polling.

Polling из этой версии основного проекта:

```sh
npm run bot:polling
```

Также существует отдельный соседний репозиторий `ishdasiz-bot` с командой `npm run start:polling`; версии больших обработчиков отличаются. Не заменяйте их друг другом без проверки функций.

Polling требует `TELEGRAM_BOT_TOKEN`, `NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`. `TELEGRAM_DRY_RUN=1` запрещён для приёма живой очереди. Новый runner сначала проверяет личность бота и состояние webhook. При действующем webhook обычный запуск останавливается. Если переключение намеренное, сначала остановите его прежний обработчик, затем выполните:

```sh
npm run bot:polling -- --switch-from-webhook
```

Команда переключения сохраняет накопленные updates. Запуск не меняет описание/профиль бота и не удаляет входящую очередь. Offset сдвигается после успешной обработки, ошибка оставляет update для повтора. Ctrl+C/SIGTERM прерывает ожидание сети и завершает текущую обработку. Содержимое updates и описание сетевого исключения не печатаются runner-ом.

## Подготовка публикации

10 октября 2026 проверены действующий проект Vercel ishdasiz-hp69 (Hobby), привязка ishdasiz.uz и метаданные Supabase. Исправления ещё не опубликованы. Найдены отсутствующие настройки Production и таблицы очереди; подробности и порядок запуска без новых платных сервисов — в [проверке готовности](docs/production-readiness-2026-10-10.md).

Перед выпуском:

1. Сверить реальную схему и историю миграций. Новые исправления собраны в [набор из 33 миграций](supabase/releases/README.md) с уникальными версиями, порядком и контрольными суммами. `npm run release:db:check` проверяет набор, `npm run release:db:prepare` создаёт отдельный локальный экспорт без подключения к базе. Старая папка содержит повторяющиеся версии и диагностические SQL: не используйте слепой `supabase db push`.
2. Проверить обязательные серверные настройки: `SUPABASE_SERVICE_ROLE_KEY`, `AUTH_SESSION_SECRET`, `CRON_SECRET`, Telegram и Eskiz. Точные имена дополнительных настроек — в исходниках серверных маршрутов. Production-вход требует работающего SMS-провайдера. Имитация SMS и тестовый код разрешены только при явном `NODE_ENV=development` или `test` без настроенного Eskiz; в неизвестном окружении отправка завершится ошибкой.
3. Проверить тариф и функцию compute. В `vercel.json` синхронизация каналов назначена каждые пять минут. [Vercel Hobby разрешает cron только раз в день](https://vercel.com/docs/cron-jobs/manage-cron-jobs); для Hobby нужна согласованная другая организация частого запуска. Не сокращайте частоту очереди молча до суток.
4. Сопоставить лимиты времени функций и фактическое время обработки. [Максимальная длительность зависит от Fluid compute и тарифа](https://vercel.com/docs/functions/configuring-functions/duration). Обработчик webhook дожидается завершения, чтобы serverless-хост не остановил работу после ответа.
5. Остановить старые отправители, согласованно выпустить схему/сайт/используемого бота/cron. Проверить права в региональных каналах, настоящее SMS-подтверждение и основные действия отдельными тестовыми аккаунтами.

Автоматическое восстановление рекомендаций и каналов не угадывает потерянные ID сообщений. Защищённые маршруты `/api/maintenance/channel-deliveries` и `/api/maintenance/recommendation-deliveries` требуют `CRON_SECRET` и явного подтверждения оператора по фактическому сообщению. Подробности и форматы запросов — в отчёте.


## Копирование перед обновлением базы

На Windows: npm run backup:database создаёт защищённый локальный архив прикладных схем public и supabase_migrations; пароль базы вводится скрыто на компьютере. npm run test:backup проверяет копирование/восстановление на отдельном локальном PostgreSQL. Реальная копия ещё не создана. Подробности и ограничения — в [описании резервного копирования](docs/database-backup.md).
